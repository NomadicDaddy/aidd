# Agent Tool Sandbox Audit Framework

> **Severity Reference**: See [SEVERITY_CLASSIFICATION.md](./SEVERITY_CLASSIFICATION.md) for issue prioritization.

> **Methodology gate**: See [AUDIT_METHODOLOGY.md](./AUDIT_METHODOLOGY.md) - read the enforcing implementation, falsify every "by design" rationale, never score from a green gate.

The agent's `bash` and file tools run **with the operator's own OS privileges** inside a target repository. There is no kernel sandbox, no container, no dropped-privilege user. The entire sandbox is a set of software checks enforced in TypeScript before a subprocess is spawned:

1. A **workspace-path boundary** - every path the model names must resolve inside the project `cwd` (`resolveWorkspacePath` in `constants.ts` for the file tools, `checkBashWorkspacePolicy` in `shell-policy.ts` for `bash`).
2. A **home-directory denial** - home and user-profile references (`$HOME`, `~`, `%USERPROFILE%`, `$APPDATA`...) are rejected outright because they expand to a path outside the project (`HOME_REFERENCE_PATTERN` in `shell-policy.ts`).
3. A **runtime-expansion denial** - constructs whose value only exists at runtime (command substitution, unbound variables, `eval`, brace expansion) are refused or statically expanded before the path check (`usesCommandSubstitution` in `shell-policy-args.ts`, `expandShellTokens` in `shell-policy-expansion.ts`).

**What this does and does not guarantee.** These checks bound the paths and constructs written **in the command string and in file-tool arguments**. They are a lexical filter, not an OS sandbox: a program the command starts (an interpreter one-liner, a repo script, a test runner, a package lifecycle hook) runs with the operator's privileges and can open any path the operator can. Audit the filter for what it claims, and record what it cannot claim under residual privileges (Section 9); do not report the tools as contained beyond the controls traced.

This audit treats **all target-repo content as untrusted input**, including any prompt, README, comment, commit message, or tool description authored inside the target repo. A hostile repo can ask the agent to read `~/.aidd/config.json` (provider API keys, web token), write outside the workspace, or smuggle a path past the regex. The filter is only as strong as the weakest path-naming construct it fails to bound - so every checklist item below is a **VERIFY against the live regex/resolver**, not a trust of its comment.

> **Evidence rule.** Trace each control from its symbol in the live source, not from a line number in this document; line anchors rot. Cite the `file:line` you actually read in the report. Bound every conclusion to the fixtures you ran and the code you traced, and say so.

> **Scope boundaries.** This audit covers **aidd's own TypeScript tool boundary** (the `bash`/file tools the model calls in-process). That boundary is reached only by the surfaces that call `executeTool`: the in-process agent loop (`NativeBackend`, used by the `native`, `lmstudio`, `ollama` and `openai` backends) and the Director chat dispatcher. It does **not** apply to the external coding CLIs: `buildBackendCommand` (`shared/src/backends/commands.ts`) launches several of them with their own approval or sandbox bypass flag (`--dangerously-skip-permissions`, `--dangerously-bypass-approvals-and-sandbox`, `--permission-mode bypassPermissions`, `--auto-approve`), so their tools run under that CLI's own rules with the operator's privileges and none of the checks below. Do not re-audit a CLI's internals here, but do record in the report which backends the path filter covers and which it does not; a claim that "agent tools are workspace-bounded" is only true for the first group. Outbound network egress from a tool subprocess is owned by [OUTBOUND_SSRF.md](./OUTBOUND_SSRF.md) - do not add an egress section to this audit. Destructive-git protection overlaps with [GIT_DESTRUCTIVE_SAFETY.md](./GIT_DESTRUCTIVE_SAFETY.md); this audit only confirms the bash-layer deny-list exists (§1), it does not re-derive that audit's scope.

## Executive Summary

**Critical Priorities**

- **Path-boundary completeness**: every shell construct that can name a path (redirect, `cd`/`pushd`, command substitution, variable expansion, glob, `cp`/`mv`/`tee` args, any other argument) is bounded or denied - no un-checked escape.
- **Home-directory denial robustness**: `HOME_REFERENCE_PATTERN` catches the double-quoted `"$HOME"` form (the policy strips single-quotes only), `${HOME...}`, `~`, `~user`, `%USERPROFILE%`, `$env:USERPROFILE`, and the `APPDATA`/`LOCALAPPDATA`/`HOMEDRIVE`/`HOMEPATH` names.
- **Secret-stripped subprocess env**: `buildToolSubprocessEnv` hands tools only runtime/shell vars - provider API keys and the web token are absent, so `env`/`printenv` in a tool `bash` cannot read them.
- **Dispatcher-level gate**: file tools are refused at the dispatcher when `allowFileEdits` is off, not merely omitted from the advertised tool list.
- **Operator-controlled edit flag**: `allowFileEdits` flows from JSON config / operator settings, never from a model-supplied argument.

**Essential Standards**

- The target repo (and any prompt authored in it) is untrusted; the path filter must hold even when the model is actively trying to escape on its behalf.
- Read/write/edit/glob/list all funnel through `resolveWorkspacePath`, which rejects absolute paths, drive-letter paths, and `..` traversal.
- A runaway `bash` is bounded by its own timeout plus `killProcessTree`, and by the backend idle monitor; the two must agree (Section 6).
- Probes use synthetic sentinels and disposable fixtures. An audit never reads, prints, or records a real credential, a real inherited environment, or real home-directory content.

## 1. Bash Path-Naming Constructs

`checkBashWorkspacePolicy` (`shared/src/agent/tools/shell-policy.ts`) runs in `runBash` **before** the command is handed to `Bun.spawn([bash, '-c', command])` (`shell.ts`). It first blanks literal output redirects to `/dev/null` (`maskNullOutputRedirects` in `shell-policy-redirects.ts`) so a stderr sink is not judged as an out-of-workspace write; `runBash` still executes the original command. `evaluateBashWorkspacePolicy` then runs its checks in a fixed, load-bearing order: destructive git, dangerous constructs, encoding+eval chains, home references and `printenv`, the unquoted absolute-path sweep, the positional checks (`cd`/`pushd`, redirects, write destinations), command substitution, and last the general argument containment sweep (`checkArgumentContainment`), which statically expands variables, resolves **every** argument against the root, and realpath-checks it for symlink escapes. Enumerate **every** way a shell command can name a path and confirm each is either bounded inside the workspace root or denied. The `/dev/null` exception is output-redirect-only: `cat /dev/null`, `rm /dev/null`, `</dev/null`, and `>/dev/null/../x` must still deny.

For every row, record at least one **negative fixture** (a command that must be denied, with the denial text observed) and one **positive fixture** (a legitimate in-workspace command of the same shape that must still be allowed). `checkBashWorkspacePolicy(command, cwd)` is a pure check for most rows, so call it directly instead of executing the command; only the symlink row needs a real directory on disk. The existing suites under `test/shared/shell-policy-*.test.ts` show the shapes already pinned; a row with no fixture there is a coverage gap to report.

A construct it does not model would be unbounded - which is why the runtime-expansion families are denied outright rather than inspected: `DANGEROUS_CONSTRUCT_PATTERN` denies `eval`, `bash -c`/`sh -c`/`zsh -c`..., `exec`, and `source`; the `ENCODING_UTILITY_PATTERN` + `EVAL_CONSTRUCT_PATTERN` pair denies any command combining a base64/base32/xxd/od utility with an eval/subshell construct; `usesCommandSubstitution` and `expandShellTokens` deny substitution and unbound expansion. **VERIFY these deny branches still fire** - construct the bypass command and confirm it is rejected, not merely that the regex looks present. A genuinely novel runtime-expansion form the patterns do not model (for example a decode utility not in the encoding set, or a shell not in the `-c` list) is still a finding, severity scaled to what it can reach. What the filter cannot bound at all - the behaviour of a program once it is running - is recorded as a residual privilege in Section 9, not as a filter bypass.

## 2. Home / User-Profile Denial

`HOME_REFERENCE_PATTERN` (`shell-policy.ts`, built by `buildHomeReferencePattern` from `HOME_VARIABLE_NAMES`) is the control that stops `cat $HOME/.aidd/config.json` and `cat ~/.aidd/config.json` from exfiltrating machine-local provider keys and the web token. The names it covers are `HOME`, `HOMEDRIVE`, `HOMEPATH`, `USERPROFILE`, `APPDATA` and `LOCALAPPDATA`, each in four spellings (`$VAR`, `${VAR...}`, `%VAR%`, `$env:VAR`), plus a leading `~`. `checkHomeReferences` tests a **single-quote-stripped** copy first (`singleQuoteStripped`), deliberately leaving double-quoted content visible because `$HOME` expands inside double quotes, and then tests the unmodified command as defense-in-depth. `printenv HOME` (or any other listed name) and a bare `printenv` are denied by `HOME_ENV_DUMP_PATTERN`. Every other variable is handled by the static expansion in Section 1, not here.

## 3. Filesystem Tool Boundary

`resolveWorkspacePath` (`constants.ts`) is the chokepoint for `read_file`, `write_file`, `edit_file`, `glob`, `list_directory` (`filesystem.ts`) and the `path` argument of `grep` (`grepWorkspace` in `shell.ts`). It rejects absolute paths and drive-letter paths and `..` escapes, then calls `verifyRealPathWithinRoot` to close the symlink-escape gap. Run every probe in this section against a disposable fixture workspace with a planted outside-root sentinel; never point a probe at a real home or config path.

## 7. Per-Run Worktree Isolation

A web-launched **coding** run can be given its own git worktree: `worktrees/<runId>` under `web.dataDir` on branch `aidd/run-<runId>`, assigned when the run is admitted (`promoteOldestQueuedRun` in `db/commands/runCeiling.ts`) and only when `web.useWorktrees` is on and the mode is `coding`. The default is **off**. Orphaned worktrees are reaped by `reapRunWorktree` (`worktreeReap.ts`) from the boot reconcile and the orphan sweep.

Keep two properties apart:

- **Working-tree isolation** (what a worktree gives): concurrent runs do not interleave edits, indexes, or uncommitted state in one checkout.

A run in a worktree has the operator's privileges over all of it. A worktree narrows the tool `cwd`; it is not a privilege boundary, and a run that defeats the path filter does **not** land somewhere harmless.

## 8. Subprocess Spawn Invariant

The invariant is about **inherited handles**, not about one API. The aidd web backend is a Bun process that holds the HTTP listen socket. On Windows, a child started from that process with `node:child_process.spawn` inherits the listening handle and keeps the port bound for as long as the child lives; `Bun.spawn` does not. So: **a child started from a process that holds a listening handle must not inherit it, and must not outlive the parent while holding it.** In the Bun backend that means long-lived and detached children go through `Bun.spawn`.

Scope the rule to that boundary. A `node:child_process` call in a process with no listening handle (the CLI, a script), or in a target whose runtime is not Bun (Node, Electron), is not a finding by itself: audit which process spawns, what handles it holds, whether the child can inherit them, and how long the child lives. A target with a different runtime needs the equivalent control for that runtime, labelled as such.

The env handed to each spawn is the explicit allowlist from `subprocess-env.ts` - tools get the runtime-only set, backend CLIs get the named provider set - so no spawn carries a `{ ...process.env }` spread.

| Check | Criteria                                                                                                                                                                                                                                                  | Remediation                                                                                                                                                                                                                                                                                 |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[ ]` | Tool subprocesses spawn via `Bun.spawn` with the scrubbed tool env - `runBash`, `grepWorkspace` (`shell.ts`)                                                                                                                                              | Confirm neither uses a `process.env` spread. These also run inside the web backend (Director chat), so the handle rule applies to them                                                                                                                                                      |
| `[ ]` | The detached run launch does not inherit the listen socket - `spawnDetachedRun` uses `Bun.spawn` with the plan from `buildDetachedRunSpawnPlan`; on Windows the spawned process is a short-lived `pwsh` `Start-Process` bridge, not the run               | Verify no `node:child_process` call on the launch path, and that the bridge exits promptly. A detached run holding the panel port is High                                                                                                                                                   |
| `[ ]` | Other backend children (`reapRunWorktree`, the git services, the app launcher) use `Bun.spawn`                                                                                                                                                            | Read each spawn site reachable from `backend/src`                                                                                                                                                                                                                                           |
| `[ ]` | Every `node:child_process` import reachable from the backend process is individually justified - today `shared/src/lib/processTree.ts` (`taskkill` in `killProcessTree`) and `shared/src/run-provenance.ts` (`execFile git`) are imported by backend code | For each: is it reached from the listening process, does the child inherit the handle, and is its lifetime bounded (timeout, short-lived by construction)? ## 9. BREAK-THE-ASSUMPTION Scenarios

> **Mandatory.** For each scenario below, construct the exact command and trace it through `checkBashWorkspacePolicy` / `resolveWorkspacePath`. **Any path-naming scenario that reaches content outside the workspace is a finding.** Never score from "the regex looks right"; the regex is a lexical filter and lexical filters have gaps.

**Fixture rules (read first).** Build a disposable workspace with a sibling **outside** directory holding a sentinel file whose content is a known non-secret string. Every "can it be read" probe targets that sentinel. The home and config commands below are for **tracing the denial** only: pass them to `checkBashWorkspacePolicy` and record the returned error; do not execute them, and never read `~/.aidd/config.json`, a real home directory, `/proc/self/environ` of a real session, or an inherited environment into a report or transcript. If a probe unexpectedly succeeds, record that it succeeded and what class of data it reached - not the data.

1. **(a) Double-quoted home read** - `cat "$HOME/.aidd/config.json"`. The first home test strips single quotes only, so `$HOME` inside double quotes remains visible to `HOME_REFERENCE_PATTERN`. **Confirm it is rejected.** If it is NOT, this is Critical (provider-key exfiltration).

2. **(b) Brace-expansion home read** - `cat ${HOME}/.aidd/config.json`. Verify the `${NAME...}` branch of `HOME_REFERENCE_PATTERN` fires, including a suffix form such as `${HOME:-/x}`.

3. **(c) In-workspace symlink escape** - in the fixture, create `./link -> <outside dir>`, then `read_file ./link/sentinel.txt` and `cat ./link/sentinel.txt`. This was a prior live finding (with the home directory as the target); it is **remediated** by `verifyRealPathWithinRoot`, called from `resolveWorkspacePath` for the file tools and from `checkSymlinkContainment` for `bash`. **VERIFY the realpath containment still holds** for both tools - confirm each is rejected with the symlink wording. A path that slips the walk (an escaping non-existent leaf, a `realpathSync` failure that is not denied, or a notional root that skips the check) is a finding.

4. **(d) Base64 / eval-smuggled path** - `eval "$(echo <base64 of a cat of the outside sentinel> | base64 -d)"`. The decoded string never appears as a literal token, so a lexical check cannot see it - which is why the **construct itself is denied** rather than inspected: `DANGEROUS_CONSTRUCT_PATTERN` rejects the `eval`, the `ENCODING_UTILITY_PATTERN` + `EVAL_CONSTRUCT_PATTERN` pair rejects the encoding+eval chain, and `usesCommandSubstitution` rejects the `$(...)`. **VERIFY each deny independently** - remove one construct at a time from the probe and confirm the others still reject it before bash runs. A runtime-expansion form none of them models is a finding, severity scaled to reachability.

5. **(e) Absolute / proc redirect (POSIX)** - `cat /proc/self/environ` and `printenv > /tmp/leak.txt`. Verify the absolute-path sweep rejects both `/proc/self/environ` and `/tmp/leak.txt` (it runs before the redirect check). Then trace `printenv > leak.txt` with an in-workspace target: `HOME_ENV_DUMP_PATTERN` only matches `printenv` followed by a listed name or a command terminator, so record whether the redirected form, `printenv -0`, `env` and `set` are denied. An allowed environment dump exposes the home path values (not provider keys) and is a finding scaled to that. Trace only. Then confirm the env that **would** leak is the stripped tool env (Section 4, synthetic source) - defense in depth, not a single point of failure.

6. **(f) Variable-assembled escape** - `a=.; cat $a$a/outside/sentinel.txt`, `cat "$PWD/../outside/sentinel.txt"`, `cat $TEMP/x`, `cat ..{,}/outside/sentinel.txt`. None of these spell `..` or an absolute path literally. Verify `expandShellTokens` judges the first two by their expanded value and denies the unbound variable and the brace form.

7. **(g) Quoted and substituted paths** - `cat "<absolute path of the outside sentinel>"` and `cat $(printf '%s' ../outside/sentinel.txt)`. The absolute sweep cannot see the first (quoted spans are blanked); confirm `checkArgumentContainment` denies it and `usesCommandSubstitution` denies the second.

8. **(h) Residual privilege: a launched program** - from the fixture, run a short interpreter command or a fixture script that opens the outside sentinel by a path the program builds itself. The path filter is not expected to stop this. Record whether it succeeded, which interpreters the tool `PATH` exposes, and what the stripped tool env and the operator's filesystem rights make reachable. This is reported as a **documented residual**, not as a filter bypass. It becomes a finding when product copy, prompts, settings text, or another audit describes the tools as sandboxed beyond the path filter, or when a cheap control that would bound it is absent where the threat model requires one.

For each: record the exact command, the policy branch that should catch it (symbol and the `file:line` you read), the observed disposition, and - when a bypass exists - what class of data it reaches. A bypass that reaches only the stripped tool env is lower severity than one that reaches the operator's config.
