# Orchestrator Concurrency Audit Framework

> **Severity Reference**: See [SEVERITY_CLASSIFICATION.md](./SEVERITY_CLASSIFICATION.md) for issue prioritization.

> **Methodology gate**: See [AUDIT_METHODOLOGY.md](./AUDIT_METHODOLOGY.md): read the enforcing implementation, falsify every "by design" rationale, never score from a green gate.

The **director** drives a cycle state machine that spawns and reconciles concurrent runs. Each cycle either resolves via a fast direct-AI path or falls back to a **detached** CLI run whose lifetime the web process does not own. Every managed launch is first **queued**, then **admitted** against the concurrency ceilings, then spawned. Runs persist to a single SQLite database guarded by a single-writer advisory lock, and concurrent runs on one project coordinate feature selection through lease files outside the database. This audit hunts the concurrency failure modes that emerge from this design: **double-spawn** of the same work, **lost transitions**, **stranded/orphaned runs** after a crash, **unbounded concurrency**, **queue starvation**, **timer disagreement** (an idle kill racing a declared timeout), and **mid-cycle crash corruption**.

The recurring structural risk: a guard that is **check-then-act** against shared state (read a count or a status, then insert/spawn) is a TOCTOU window unless the check and the act are one serialized step. For database state the closure is specific: a multi-statement atomic write must be a command in `db/commands.ts` / `db/commands/*` that runs inside the DB **worker's** `db.transaction()` (`createInProcessCommands`; callers wrap it in `withSqliteRetry`), or a **single** conditional statement (`UPDATE ... WHERE status = <expected> RETURNING`) whose result the caller checks. An inline `db.transaction()` at a call site is NOT acceptable (the backend SQLite lives in a Bun worker; a call-site transaction runs on the wrong connection; see the web-DB-worker architecture). For filesystem state the closure is an exclusive create (`wx`). This audit verifies each invariant against the actual admission/executor/reconcile/persistence code, not against the comment that asserts it.

> **Evidence rule.** Trace each control from its symbol in the live source, not from a line number in this document; line anchors rot. Cite the `file:line` you actually read in the report. Bound every conclusion to the interleavings you traced or drove, on the platforms you ran them on, and name the ones you did not exercise.

## Executive Summary

**Critical Priorities**

- **No double-spawn**: a suggestion cannot be launched twice, and two runs cannot claim the same feature. Verify the compare-and-set claim in `launchSuggestion` (`suggestionService.ts`) and the exclusive feature lease (`shared/src/metadata/feature-leases.ts`) both hold under race.
- **Max-concurrency bound holds under race**: `launchRun` only inserts a `queued` row (`insertQueuedRun`); the count read and the `queued -> running` promotion are **one** worker transaction in `promoteOldestQueuedRun` (`db/commands/runCeiling.ts`), with the per-project ceiling enforced in the same transaction, and only a promoted row is ever spawned (`admitQueuedRuns` in `run/admission.ts`).
- **A slot is never leaked or double-counted**: a promoted row whose spawn fails is released or driven terminal, and a queued row that is cancelled is never spawned.
- **Restart reconciliation is deterministic**: detached runs and stale `running` cycles re-attach when the run is observably alive and fail cleanly when it is not (`activeRunReconcile.ts`, `cycleReconcile.ts`); a healthy survivor is never failed, a dead one never resurrects.
- **Single-writer invariant**: the writer lock (`db/writerLock.ts`) prevents a second backend from interleaving writes against the same data dir.
- **Transactional persistence**: a mid-cycle crash leaves no half-written cycle (`cyclePersistence.persistCycleResult` runs suggestion inserts + terminal update in one transaction).

**Essential Standards**

- Stop/kill vs natural-completion does not leave a zombie heartbeat or a frozen activity state.
- Scheduled, manual, and chat-triggered cycles never stack: every entry point starts through one atomic idle gate.
- Detached runs survive a restart via the heartbeat watcher, with exactly-once reconciliation.
- The idle monitor and a tool call's declared timeout agree: a call is not killed inside the time it declared, and a declared time cannot disable the idle guard.
- A durable obligation left open by a crash (an auto-launch decision) is claimed once and finished once.

## Applicability & Scope

**Full applicability**: an agent-orchestration tool with the aidd shape - a director or scheduler, detached agent runs, and a persisted multi-run state machine reconciled across restarts.

**Partial applicability (portable equivalents)**: do not require all of those at once. Following the reduced-equivalent principle of [AUDIT_METHODOLOGY.md](./AUDIT_METHODOLOGY.md) Rule 4, when the target lacks an aidd-specific mechanism, find the **reduced equivalent** and audit that instead of recording N/A. Real lifecycle and concurrency risks have been found in targets with no Director, no agent tools and no git pipeline. Any target that does one or more of the following is in scope for the matching sections:

### Probe Safety

Drive interleavings in a **disposable fixture**: a throwaway data directory and database, a throwaway git repository, a non-default port, and a stub or simulated child in place of a real agent backend. Do not race launches, kill processes, or restart against the operator's live panel, its database, or a run in progress, and do not start a real (billable) backend session to create load. Where an interleaving cannot be driven safely, trace it by hand and say so.

## 1. Single-Writer & Transaction Atomicity

`acquireWriterLock` (`db/writerLock.ts`) is an **advisory** sidecar-file lock recording the owning pid; it is acquired when the database is opened and released on shutdown, with stale-lock self-heal. The `heldLocks` in-process registry rejects a same-process double-acquire that the on-disk check alone could not distinguish from a stale leftover.

| Check | Criteria                                                                                                                                                                                                                                                                                                                                   | Remediation                                                                                                                                                                                                |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `[ ]` | Exactly one backend can hold the writer lock: `writeLockExclusive` uses `flag: 'wx'` (atomic create-or-fail)                                                                                                                                                                                                                               | Verify the `EEXIST` branch is the race-resolution primitive                                                                                                                                                |
| `[ ]` | A second backend pointed at the same data dir is rejected with a fatal error, not silently allowed to interleave writes                                                                                                                                                                                                                    | Confirm a live holder (different pid, `isProcessAlive`, corroborated by `isLockCorroborated`) throws                                                                                                       |
| `[ ]` | A crashed backend's stale lock self-heals: a dead holder or reused pid is reclaimed                                                                                                                                                                                                                                                        | Verify the reclaim path does not race two reclaimers into both acquiring, and that a recycled pid belonging to an unrelated live process does not block startup forever                                    |
| `[ ]` | The lock guards the **process**, not individual transactions; verify that within the one writer, the cycle/run writes that MUST be atomic use an actual transaction or a single conditional statement, not just the lock                                                                                                                   | The writer lock does NOT serialize check-then-act inside the process; Sections 2-3 depend on this distinction                                                                                              |
| `[ ]` | Each multi-statement atomic write is a **command** in `db/commands.ts` / `db/commands/*` run inside the **worker's** `db.transaction()` (`createInProcessCommands`), NEVER an inline `db.transaction()` at a call site: the backend SQLite runs in a Bun worker, so a call-site transaction runs on the wrong connection and is not atomic | Grep call sites for `db.transaction(`; any outside `db/commands*` is a finding. | `[ ]` | Every single-statement compare-and-set outside a command checks its result: the caller reads `RETURNING` (or the changed-row count) and stops when it lost                                                                                                                                                                                 | List each guarded `UPDATE ... The same logical work can be triggered through multiple entry points: `launch_suggestion`, `launch_run`, `run_cycle` (`dispatchOrchestrateTool` in `director/chatAgentTools/dispatch.ts`), the panel's own launch routes, the Director's suggestion auto-launcher, a standalone CLI invocation, and the built-in Director scheduled task. Three separate guards cover them, and each must be verified by itself: the **suggestion claim** (one launch per suggestion), the **cycle idle gate** (one cycle at a time), and the **feature lease** (one run per feature, across every entry point).

## 3. Max-Concurrency Bound

Launch is **queue first, execute on admission**. `launchRun` (`run/launch.ts`) inserts the row as `queued` through `insertQueuedRun` and then calls `admitQueuedRuns` (`run/admission.ts`). Admission loops on `promoteOldestQueuedRun` (`db/commands/runCeiling.ts`), a **single** immediate-mode worker transaction that counts `running` managed rows, walks queued rows oldest first, and flips the first eligible one to `running`. Only a promoted row is spawned (`spawnPromotedRun`). A launch over the ceiling is not rejected: it stays `queued` and is admitted later. Queued rows do not consume a slot.

The spawn comes **after** the promotion on purpose. The detached hop is one-way, so a spawn-then-check launch that lost the race would leave a live run with no row.

## 5. Restart Reconciliation

Two passes run at boot, before the server listens and before scheduling is wired (`backend/src/start.ts`): `reconcileStaleRuns` (`run/activeRunReconcile.ts`) for `running` run rows, then `reconcileStaleCycles` (`director/cycleReconcile.ts`) for `running` director cycles. A periodic `sweepOrphanedRuns` (`run/activeRunSweep.ts`) covers runs that died before writing any heartbeat.

Run survival is decided by **observation, on every platform**: the heartbeat file and pid liveness. A fresh heartbeat resumes; a terminal heartbeat terminalizes; a missing heartbeat fails; a stale heartbeat fails only when the pid is absent or dead. On POSIX the detached child is the run. ## 7. BREAK-THE-ASSUMPTION Scenarios

> **Mandatory.** Construct the interleaving that double-spawns or strands a run, and trace it against the lock, admission, lease, executor, reconcile and persistence code by hand, or drive it in the disposable fixture (see Probe Safety). **Any interleaving that double-spawns, exceeds the concurrency bound, kills a healthy run, or strands a run is a finding.**

1. **Double-launched suggestion (CAS-guarded; falsify the guard)**: fire two `launch_suggestion` calls for the same `pending` suggestion id simultaneously. Both read the row as `pending`, but the spawn is gated by an atomic compare-and-set in `launchSuggestion`: `UPDATE suggestions SET status='launching' WHERE id=? AND status='pending' RETURNING id`. Exactly one caller's update returns a row and reaches `launchRun`; the loser updates zero rows and throws `SuggestionClaimLostError`. Trace both interleavings and confirm only ONE run is queued. Then probe the edges: a launch failure after the claim releases the row to `pending`; an orphaned `launching` (the launcher died between the claim and the `launched` write) is retired by the next completed cycle. Race the operator's click against the Director's own auto-launcher for the same suggestion as well. The race is closed unless the `WHERE status='pending'` predicate is dropped or the claim is split from the launch.

2. **Same feature from two entry points (lease-guarded; falsify the guard)**: launch a suggestion that targets a feature, and at the same time start a second coding run on the same project - once from the panel, once as a standalone CLI run, once in a linked worktree. The guard is the feature lease: exclusive `wx` creation under git's common directory, shared by every checkout. Confirm exactly one run holds the feature and the other skips to the next candidate or stops lease-blocked. Then the lifecycle: the holder finishes (lease released), the holder is killed hard (lease reclaimed by the next acquirer or reaped by the web), and a live holder's lease survives two contenders racing to steal a dead one. Separately confirm the checkout itself: without worktrees, admission clamps mutating runs to one per project (`effectiveProjectRunCeiling`), but a standalone CLI run is outside that count. The finding is two runs on one feature, a lease that outlives a dead owner, a live lease destroyed, or two mutating runs interleaving in one checkout with nothing but the lease between them. Cross-reference GIT_DESTRUCTIVE_SAFETY.md for the snapshot-diff consequence.

3. **Concurrency bound under a burst (atomic admission; verify it stays closed)**: with `maxConcurrentRuns = N`, fire N + 2 launches at once across two projects. Every launch inserts `queued`; `promoteOldestQueuedRun` counts and promotes in one immediate transaction, so exactly N rows are `running` and two stay `queued` - none is rejected, none overshoots. Then: end one run and confirm the **oldest eligible** queued row is admitted; cancel a queued row and confirm it is never spawned; force a spawn failure on a promoted row and confirm the slot is released and the next row is admitted; start a standalone CLI run and confirm the count is unaffected. The finding is N + 1 running, a queued row that never starts while eligible, a cancelled row that starts, or a slot lost to a failed spawn.

4. **Kill the backend mid-cycle, then restart (observe both outcomes)**: start a cycle in CLI-fallback mode (detached run), stop the web backend while the run is `running`, restart. On boot the writer lock is reclaimed, `reconcileStaleRuns` settles the run and `reconcileStaleCycles` settles the cycle. Exercise **both** cases in the fixture, on each platform audited: (a) the detached run is still **alive** - it must be re-attached and allowed to finish, with its pid taken from the heartbeat; (b) the detached run is **dead** - it must be failed exactly once, its worktree and leases reaped, and its cycle failed or advanced. Do not assume the Windows outcome from the platform: the launch goes through a detached bridge precisely so the run survives, so observe it. A live run that is force-failed and a dead run that is re-attached are both findings. Also verify: (c) exactly one outcome per stale cycle; (d) no second awaiter if reconcile is invoked again while the first is waiting; (e) no zombie heartbeat surfaces after the terminal write.

5. **Scheduled vs manual cycle stack (gated; falsify the gate)**: with the built-in Director task active, time a manual `run_cycle` to land alongside a due scheduled occurrence. There is no check-then-start window: both paths call `startDirectorCycleIfIdle`, which selects the `running` cycle and inserts the new row in one worker transaction, so the loser never inserts. Confirm exactly one `running` row across the race, that the manual loser surfaces a 409 rather than a silent no-op, and that the scheduled loser is recorded `skipped` with its cadence already advanced by the claim. The finding returns only if a caller inserts a `director_cycles` row outside the command, or the gate's select and insert are split.

6. **Long tool call vs the idle monitor**: with a stub backend, emit a `tool_call` that declares `timeout_ms` longer than the backend's idle `killMs` and then stay silent. Confirm the run is not idle-killed inside the declared time, is killed once the declared time (capped at 30 minutes) plus `killMs` has passed, and that the same silence with no declared timeout is killed at `killMs`. Repeat with an abort mid-call and with the run's wall-clock limit expiring mid-call. The finding is a call killed inside its declared time, a declared time that disables the guard, or a backend still running after the monitor reported the kill.

7. **Crash around the auto-launch decision**: let an automatic cycle complete with auto-launch enabled, and stop the backend (a) after `persistCycleResult` but before the dispatch, then (b) after the claim but before finalize. Restart each time. Confirm `resumeAutoLaunchDecisions` dispatches the cycle once, under the bounds preserved with the cycle, and that case (b) waits for the claim to go stale and does not relaunch a suggestion the dead dispatch already launched. The finding is suggestions never considered, considered twice, or judged under bounds widened after the cycle completed.

For each: record the entry points raced, the check-then-act (or the guard that closes it) with the `file:line` you read, the observed or traced outcome, the platform, and the invariant violated.

## False Positives Considered and Rejected

This section is REQUIRED: if you found zero false-positive candidates, state that explicitly. Common candidates to document: the writer lock NOT serializing per-transaction (by design: it guards the process; the TOCTOU fix belongs in the transaction, not the lock); a launch over the ceiling staying `queued` instead of being rejected (by design: queue then admit); standalone CLI runs not counted against the managed ceilings (declared policy, IF the same-checkout consequence is guarded); the resumed-cycle `void ...catch(...)` fire-and-forget (intentional non-blocking re-attach, IF a second awaiter is provably impossible); director cycles bypassing `resolveProjectPath` (intentional: they run in a neutral cwd).

| Candidate                                                                                                                        | Disposition                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Writer lock does not serialize per-transaction; it is acquired once when the database opens, not per write (`acquireWriterLock`) | **Not a finding.** By design: the advisory lock guards the **process** (exactly one writer per data dir). Check-then-act atomicity belongs in a worker transaction (`promoteOldestQueuedRun`, `persistCycleResult`, `startDirectorCycleIfIdle`) or a checked single-statement compare-and-set, not the lock. The lock and the transaction are complementary layers, not substitutes.                                                            |
