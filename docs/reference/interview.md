# Interview Mode

Interview mode walks a project through a sequence of questions, recording one answer at a
time into project metadata. It is how aidd gathers the human context it cannot infer from
code (product intent, constraints, priorities). It can be driven from the CLI or from the
**Interview** tab on a project's detail page. The two surfaces group questions differently and
write answers in different places, but the web reader understands both answer formats; see
[Two surfaces, interoperable answers](#two-surfaces-interoperable-answers).

## Files

| Path                           | Role                                                                                                       |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| `.aidd/questions.md`           | The question set. Default path; override with `--interview FILE`.                                          |
| `.aidd/responses/responseN.md` | One file per question answered by the CLI. Not written by the web tab.                                     |
| `.aidd/responses.md`           | Written by both surfaces, differently: a progress table by the CLI, the answers themselves by the web tab. |

## CLI

```powershell
bun run start -- --project-dir C:\path\to\my-app --interview
```

If `.aidd/questions.md` does not exist, the first iteration generates it: the agent reads the
codebase and `.aidd/` metadata and writes `## ` sections whose headings contain a question
mark. Three iterations that end without a parseable questions file end the run as flailing
(`cli/src/modes/interview-generate-questions.ts`).

Once the file exists, each iteration selects the first **unanswered** question, prompts the
backend, writes the answer to `.aidd/responses/responseN.md`, and rewrites the
`.aidd/responses.md` progress table. A question counts as answered once its response file
exists. The run keeps iterating until every question has a response file or it hits a stop
condition such as `--max-iterations` (unset by default), so one invocation normally works
through the whole set (`cli/src/modes/interview.ts`).

The CLI parser treats each `## ` section containing a question mark as one question, skipping
sections titled "Legend" or "Summary"; when no heading section qualifies it falls back to
every line ending in `?` (`cli/src/modes/interview-questions.ts`).

## Web

The project detail **Interview** tab (`frontend/src/pages/projects/detail/InterviewTab.tsx`)
shows answered/total with a completion bar, lists unanswered questions as collapsed rows that
expand into an answer box (filterable by priority, searchable by prompt text, 12 per page),
and renders answered questions read-only. It reads inline web answers and follows canonical
`responses/responseN.md` links from a CLI progress table. Submitting an answer rewrites
`.aidd/responses.md` into the inline web format while preserving every linked answer it read; it
does not delete or write anything under `.aidd/responses/`.

API (`backend/src/routes/projects.ts`, served by
`backend/src/services/interviewService.ts`):

| Endpoint                                        | Purpose                                   |
| ----------------------------------------------- | ----------------------------------------- |
| `GET /api/v1/projects/:id/interview`            | Progress + answered/unanswered questions. |
| `POST /api/v1/projects/:id/interview/responses` | Submit `{ questionId, answer }`.          |

Both return the same payload, nested under an `interview` key: `answered`, `total`,
`hasQuestionsFile`, `answeredQuestions`, and `unanswered`. Each question carries an `id`,
`priority`, and `prompt`; answered ones also carry `response`. A missing `questions.md`, an
unknown `questionId`, or a whitespace-only answer fails the POST with a 400.

## Two surfaces, interoperable answers

The CLI and the web tab still use different question models and write different answer formats:

- The web tab parses only `- **[PRIORITY]** prompt` list items; headings merely delimit
  sections, and `Legend` and `Summary` sections are skipped. A questions file generated by CLI
  interview mode uses `## ` question headings instead, so the tab reports "The interview file
  is present but contains no parsed questions."
- The `onboarding-interview` skill (`skills/onboarding-interview/SKILL.md`) writes the
  `- **[PRIORITY]**` form the tab expects.
- The CLI reads answers from `.aidd/responses/responseN.md`. The web tab writes them inline in
  `.aidd/responses.md`, as a `  Response: ...` line under a repeat of the question line.
- The web tab also reads a CLI-written progress table. It follows only canonical
  `responses/responseN.md` links below the selected project's `.aidd/` directory, extracts the
  `## Question` priority bullets and `## Response` body, and binds that response to every covered
  bullet. Prompt matching tolerates typography-only dash, quote, arrow, and whitespace changes
  between the committed question and response documents.

## Relationship to onboarding

Every compiled prompt lists the interview files as project context: the onboarding prompt as
"Interview prompts" (`/.aidd/questions.md`) and "Interview answers" (`/.aidd/responses.md` +
`/.aidd/responses/*.md`), the coding, directive, audit, todo, and validate prompts as optional
interview context. The answers are therefore available to the runs that (re)generate
`.aidd/spec.md` and the feature backlog. See [auto-rebuild.md](./auto-rebuild.md).
